## What the 212 failures actually mean

The old route audit rejects every `data-ad-placement` attribute as a disabled
placeholder. Current production intentionally uses the same attribute on live ad
wrappers (`data-ad-mode="live"`), with an initially hidden fallback. This produces
209 false positives. It is not evidence that all 209 pages display placeholders.

The replacement static contract distinguishes the live and explicitly disabled
modes, checks approved placement/client/unit identities and duplicates, and rejects
visible placeholders in live markup. Responsive sidebar units mount after browser
`matchMedia`; their SSR wrappers therefore need not already contain an `ins` unit.
The existing browser advertising tests still check actual responsive placement,
fill and protected global suppression behavior. The new checker is not a policy
certificate or proof of real-network rendering, DOM ancestry, or every template's
complete placement inventory. It correlates units by approved slot IDs across the
document, not by parent-child nesting.

Nine mutation-focused Node tests cover missing/wrong/duplicate units, unknown or
duplicate placements, wrong clients/modes, visible fallbacks, responsive SSR,
disabled-mode expectations and ad-free indexed pages. The noindex guard is unchanged.

The audit still **fails with three real policy mismatches**:

- `/categories/health-and-wellness-word-searches`
- `/collections/brain-training-word-searches`
- `/guides/how-hidden-message-word-searches-work`

Their metadata correctly says noindex, but the category/collection/guide templates
choose monetized shells unconditionally, rather than using the record's publication
eligibility. This is a source-supported explanation and a reproduced markup defect.
Correcting their ad eligibility would change advertising placement/behavior, which
is not authorized in this overnight run. Leave that implementation **awaiting owner
approval**, with a separate placement/eligibility plan, real-network acceptance and
rollback under `ai-issues/AD-PLACEHOLDER-SAFETY.md`. Do not mark those defects fixed.

The parent milestone's complete Lighthouse run failed best practices at 77 on its
eight mobile and three desktop checks; an earlier run returned 96. A pristine-main
homepage/generator comparison reproduced 77, with `third-party-cookies` and
`inspector-issues` and no Lighthouse runtime error. The overnight two-page probe
against this branch's own export at port 3240 reproduced best practices 77 on
both pages, the same two failed audits, and no runtime error. That probe used
the existing Lighthouse/chrome-launcher packages with all four categories enabled;
it was a focused comparison, not another complete 11-case audit.

These external-network/browser findings differ from deterministic local unit,
SEO or static-export failures. Do not turn off ads, alter loading/fill detection,
relax the best-practices threshold, or claim field CWV/compliance based on this
investigation. Review actual provider/consent behavior separately. The old launch
checklist contains historical pre-live-ad assumptions; its old zero-ad/zero-audit
claims are dated evidence, not current findings.
