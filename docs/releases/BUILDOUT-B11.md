## Shared guarantees and gaps

Each route uses `IndexablePage` with its declared alphabet pack, eight example entries, medium preset and a route-derived seed; the hidden-message route supplies `GREAT JOB`. In the fixed default samples, all eight entries were placed for each of the 13 routes, with no exclusions or warnings; this does not establish general correctness. `generatePuzzle` and the shared request/share decoder, printable component, solver and PDF renderer handle the result. Generation is deterministic for the same complete request. Share state includes title, exact input, seed, alphabet, sizing, directions and hidden message: it is encoded, not encrypted, and may expose supplied text to anyone receiving the link or QR. A replay is only as reliable as the same generator/normalization implementation; changing it requires a migration and old-link/fingerprint validation. The solver accepts stored placement paths (also reversed), not every incidental occurrence. Current request validation bounds dimensions, lengths and workload, but does not establish that symbols represent a particular language or that every intended word is placed.

The builder warns on excluded words and some no-token inputs, but normalized duplicates are filtered without being counted as excluded. Latin-family normalization strips diacritics and removes unsupported characters; a label can therefore differ from the tokens placed. One-character words can be generated but `findMatchingPlacement` rejects paths shorter than two cells. Preview/print answer markup uses placed coordinates, but this audit's static rendering tests do not establish real-device print, screen-reader usability, correct visual font fallback, QR scanning, accurate content, or tactile readability. The PDF renderer's standard font explicitly rejects unsupported glyphs rather than embedding a general Unicode font. Multi-character cell font sizes shrink with token length; actual print legibility and clipping require measured, real-output review. Shared print CSS hides the site ad slots, but source inspection and mocks do not certify actual ad-network behavior.

`getAlphabetPack(...).tokenLabel` exists but no production component calls it: the playable grid's accessible cell name contains the raw displayed token, and the static preview grid is one labelled SVG image. There is no specialty-specific conversion legend in `PrintablePuzzle` or the PDF renderer. The builder's alphabet selector lists Latin, Morse, Braille, binary, hex, Greek, kana and ASL; Spanish, French and emoji presets are absent from its option list, creating an unverified displayed-selector/state mismatch on those three routes. Confirm this in a real browser before selecting a repair. The page's intro and status string are source assertions, not a conformance test.

## Route-by-route disposition

All routes below need further review before claims of full support or indexing. “PDF baseline” applies only to the stock route sample and the existing local standard-font PDF generation test, not arbitrary input or print layout. “Browser print” means the shared SVG/HTML path exists, not that a specific printer, device, screen reader or tactile medium was validated.

| Route | Current token behavior / PDF baseline | Readiness blocker and bounded next work |
| --- | --- | --- |
| Morse code | Latin letters/digits map to dot/dash strings, or whitespace/slash-separated raw dot/dash groups; sample PDF uses supported ASCII. | The route promises a printable legend, but neither print renderer contains one. Raw groups are not checked against a code table; reject or clearly identify invalid groups and review separator/word-boundary behavior against ITU. Measure multi-character cells and verify legend/keyboard/print. |
| Braille | Maps A–Z to Unicode Braille pattern glyphs; digits pass through as ordinary digits. Default sample PDF rejects unsupported glyphs; HTML/SVG print path exists. | Visual Unicode cells are not a tactile output or a complete Braille transcription; code indicators, numbers, language and contraction rules need specialist review. Verify accessible descriptions and output device, and do not claim tactile compatibility from Unicode alone. |
| ASL fingerspelling | ASCII `ASL-A` etc. text per Latin letter; sample PDF can encode that text. | No handshape or movement representation is implemented; this is a label scaffold rather than a fingerspelling display. Review with Deaf/ASL experts, asset rights and accessible descriptions before claiming ASL support. |
| Semaphore | Uses the generic emoji/symbol pack, not flag positions; sample PDF rejects unsupported glyphs. | A symbol scaffold is not semaphore. Review a sourced representation, alternative text and licensed graphics; until then treat as not implemented for semaphore. |
| Binary | Uppercased normalized Latin letters/digits are encoded as 8-bit character-code strings per grid cell; sample PDF is generated. | It is not a bit-per-cell puzzle, and 8-character tokens shrink in cells. Measure text in preview, PDF and print; disclose exact encoding and input constraints. |
| Hexadecimal | Uppercased normalized Latin letters/digits map to hexadecimal character codes per cell; sample PDF is generated. | Clearly state character-code rather than raw-byte input semantics; measure output and validate intended classroom examples. |
| Roman numeral | Ordinary Latin pack and English number vocabulary; sample PDF is generated. | No numeral conversion, numeric range, or Roman-symbol grammar exists. Treat as standard text scaffold; design and test conversion and invalid inputs before claiming a numeral generator. |
| Greek alphabet | Latin input mapped letter-by-letter to Greek-looking tokens; mappings collide (C and G both Γ). Native Greek input is stripped by Latin normalization; sample PDF rejects glyphs. | This is neither native Greek input nor validated transliteration. Scope a correct native-script approach with language review, collision/solver tests, font support and old-link migration. |
| Spanish | Same Latin normalization; `año` and `ano` both become `ANO`, while labels retain original spelling; stock ASCII sample PDF is generated. | Ñ is a distinct Spanish letter; loss can change meaning and silently deduplicate. Design explicit locale-aware policy, duplicate reporting, PDF fonts and selector behavior; migration must protect old seeds/links. |
| French | Same Latin normalization: `noël` → `NOEL`, while `cœur` → `CUR` because `œ` is removed rather than expanded. Stock ASCII sample PDF is generated; non-ASCII labels may fail. | Define a reviewed normalization and display policy for accents and ligatures, address Unicode PDF and selector mismatch, and validate old-link compatibility before changing. |
| Japanese kana | Maps Latin letters individually to a small Katakana-looking table: `ka` → `カ` + `ア`. Native kana input is stripped; sample PDF rejects glyphs. | This is not general Japanese input or a validated romanization conversion; require native script/tokenization and language review, collision checks and font support before Japanese claims. |
| Emoji | Maps A–Z to a small geometric-symbol table, including collisions (E and S → ★); direct emoji input is not implemented. Sample PDF rejects glyphs. | Disambiguate symbols and word-to-token mapping, provide actual meaningful accessible labels and a legend, test Unicode print and the missing selector option. Do not call every geometric shape an emoji. |
| Hidden message | Latin puzzle fills remaining cells row-major with hidden-message tokens, then filler; the stock `GREAT JOB` request is encoded in share state and sample PDF is generated. | Overflow warns and applies only what fits; it is not an all-or-nothing promise. Specify how to find/read the message, display capacity before export and test no-message, exact-fit/overflow, answer keys and privacy of shared state. |

## Priority review queue

1. Resolve misleading semaphore, Roman numeral, ASL, native Greek/kana, Spanish/French and emoji claims through an owner-reviewed truthful product decision; do not change advertising, canonicals or indexed content as an incidental fix. Verify the selector behavior in a browser. Avoid unreviewed symbol artwork.
2. Design a shared pre-export integrity summary (duplicates, unsupported tokens and unplaced entries) with actionable recovery, including one-character solver paths and hidden-message capacity. Treat any normalization change as a versioned compatibility migration for old links and their output fingerprints.
3. For each supported scope, execute actual browser play/keyboard and screen-reader workflows, all utility/QR/share replay, SVG/print and PDF output on representative devices. Inspect 8-bit cell readability and unsupported-font recovery. No generic test or route status proves all languages or symbols.
4. Require informed language/community and cultural review, provenance/licensing of any graphic assets, and deliberate output-font/tactile-device selection before semantic or accessibility claims. Keep unsupported scopes noindex until separately approved; this is a planning status, not a change in publication state.

## Primary references

- [ITU-R M.1677-1 International Morse code](https://www.itu.int/rec/R-REC-M.1677-1-200910-I/) is a reference for a future code-table and separator review; this audit does not certify conformance.
- [Unicode Standard, chapter 21](https://unicode.org/versions/Unicode17.0.0/core-spec/chapter-21/) distinguishes Braille patterns from language-dependent associations and tactile rendering; a Unicode glyph alone does not provide embossed output.
- [NIDCD: American Sign Language](https://www.nidcd.nih.gov/health/american-sign-language) describes fingerspelling and its handshapes; no handshape assets are present in this route.
- [RAE orthography appendix](https://www.rae.es/diccionario-estudiante/docs/ortografia.pdf) lists Ñ separately in the Spanish alphabet. [Dictionnaire de l’Académie française: cœur](https://www.dictionnaire-academie.fr/article/A9C2813) demonstrates the `œ` spelling used in the test.
- [Government of Japan overview](https://www.gov-online.go.jp/eng/publicity/book/hlj/html/201902/201902_08_en.html) identifies hiragana and katakana as writing systems; the observed per-Latin-letter mapping does not validate Japanese language support.
